# Spec: 研究任务处理环与写回安全

Status: ready-for-agent
Feature slug: `research-loop`
Sources: `CONTEXT.md`、ADR-0001、ADR-0004、ADR-0005、ADR-0006、现有 `processor-loop` 规格、当前本地联调问题记录和已确认的研究 skill 决策

## Problem Statement

当前处理环已经可以把口播写入当日日记，并在模型判断为独立想法时创建 `Yan帳/想法`。当口播包含明确的认知缺口时，系统只能写入 `needs_research: true`，研究 runner 尚未接入，因此用户看不到 `Yan帳/研究` 中的研究简报。

当前本地联调还暴露出三类处理问题：

1. 处理环连续收到多条口播时，唤醒事件逐条排队，单个模型调用耗时较长，用户难以判断内容是否已经进入 AI。
2. agent 可能修改收件箱文件，机械验收拒绝整轮；agent 也可能只在回执中交代部分收件项，导致其他原文继续留在收件箱。
3. 研究或想法文件可能被写入日记树下的嵌套 `Yan帳`，形成与顶级 `Yan帳` 并存的错误目录。当前有效目录必须保持在 vault 顶层。

用户希望处理环能自动识别需要研究的想法，并默认直接完成研究：优先使用国外和国际来源，结合原始资料、独立资料、反方观点和多视角分析，写入带证据的研究简报，同时保留来源双链。研究阶段需要给出技术可行性、证据边界和未知点，不能把高风险主题写成医学诊断或确定性结论。

## Solution

把处理环扩展为两个连续阶段，并由同一个编排循环和单实例锁控制：

1. 内容整理阶段读取 `_inbox`，把口播轻整理写入当日日记，按想法轴创建顶层 `Yan帳/想法`，按待查轴生成研究任务候选。
2. 研究阶段自动消费已确认的研究任务候选，调用独立研究 skill 搜集和核验证据，写入顶层 `Yan帳/研究`，更新来源笔记状态并建立双向链接。

研究阶段默认开启，不设计 `off`、`ask`、`auto` 或其他用户权限模式。研究范围不预先限制地区、语言、来源数量、观点数量或问题领域。来源策略固定为国外和国际来源优先，国内官方资料只能作为本地政策、制度文本、当事方立场或本地事实的补充，不能单独支撑关键结论，并需要用国外、国际或独立来源交叉核验。

编排脚本继续拥有收件箱删除、路径验收、失败计次、隔离和生产发布权。agent 对收件箱完全只读，只能写入允许的正文、研究、状态和回执路径。任何嵌套 `Yan帳`、收件箱修改、回执漏报或旧回执复用都使本轮失败，并尽可能恢复危险变更。

## User Stories

1. As a 使用者, I want 含有明确认知缺口的口播自动进入研究任务, so that 我不需要再次手动触发调研。
2. As a 使用者, I want 纯日常口播只进入当日日记, so that 普通生活记录不会被无关研究打扰。
3. As a 使用者, I want 独立想法继续写入 `Yan帳/想法`, so that 想法可以脱离日期长期回看。
4. As a 使用者, I want 想法轴和待查轴可以同时成立, so that 一个产品想法可以同时拥有想法笔记和研究任务。
5. As a 使用者, I want 研究任务可以来自当日日记或想法, so that 我可以从时间线或长期主题发起研究。
6. As a 使用者, I want 研究任务使用原始口播的真实问题, so that 研究范围不会被模型擅自改成另一个主题。
7. As a 使用者, I want 研究任务在问题模糊时明确记录假设和边界, so that 研究结果的适用条件可回看。
8. As a 使用者, I want 五条连续投递被同一个处理循环有序消费, so that 我能看到所有条目最终都有处理结果。
9. As a 使用者, I want 处理环合并连续唤醒信号, so that 多次快速投递不会创建大量重复处理轮。
10. As a 使用者, I want 投递成功只表示进入收件箱, so that 我不会把投递结果误认为研究已经完成。
11. As a 使用者, I want 研究任务完成后看到 `Yan帳/研究` 中的一条简报, so that 我可以在 Obsidian 中持续回看结论和依据。
12. As a 使用者, I want 研究简报包含结论摘要, so that 我能快速判断是否值得继续阅读。
13. As a 使用者, I want 研究简报保留事实、推断、建议的区别, so that 我能判断哪些内容来自来源，哪些内容来自分析。
14. As a 使用者, I want 研究简报列出证据和来源链接, so that 我可以复核关键结论。
15. As a 使用者, I want 研究简报列出未知点和证据限制, so that 研究结果不会制造虚假的确定性。
16. As a 使用者, I want 研究简报包含不同观点和反方审查, so that 我能看到最可能推翻结论的证据或条件。
17. As a 使用者, I want 研究简报优先使用国外和国际资料, so that 核心判断建立在更广泛的外部资料上。
18. As a 使用者, I want 国内官方资料被标明为立场或本地事实来源, so that 它不会无标记地成为关键结论的唯一依据。
19. As a 使用者, I want 研究覆盖不同语言和来源类型, so that 语言或地区不会提前缩小证据范围。
20. As a 使用者, I want 研究在新增来源不再改变结论、证据强度和未知点时停止, so that 来源扩展有合理的停止条件。
21. As a 使用者, I want 研究简报记录来源标题、作者或机构、日期和访问日期, so that 资料具备可追溯性。
22. As a 使用者, I want 无法核验的来源明确标记为未知, so that 系统不会编造 URL、论文或数据。
23. As a 使用者, I want 研究简报回链到来源日记或想法, so that 我能知道研究为什么产生。
24. As a 使用者, I want 来源日记或想法回链到研究简报, so that 双链能够从原始想法和研究结果两个方向导航。
25. As a 使用者, I want 研究完成后 `needs_research` 被正确关闭, so that 处理环不会无限重复同一个任务。
26. As a 使用者, I want 研究部分完成或失败时保留 `needs_research: true`, so that 证据不足的任务仍然可以继续。
27. As a 使用者, I want 研究失败时原始口播和想法正文仍然保留, so that 外部来源问题不会造成内容丢失。
28. As a 使用者, I want 研究过程发现的新问题被列入后续任务, so that 研究可以形成可追踪的下一步。
29. As a 使用者, I want 研究过程产生的新想法不会覆盖原始想法, so that 原始记录和后续推断保持独立。
30. As a 使用者, I want 三大项视频分析这类想法可以研究技术可行性, so that 我能知道动作指标、视频条件、模型和数据要求。
31. As a 使用者, I want 三大项视频分析研究区分可观察动作异常和伤病判断, so that 系统不会把视频分析写成医学诊断。
32. As a 使用者, I want 健康相关研究标出需要专业判断的部分, so that 研究结果不会被误用为个人医疗建议。
33. As a 使用者, I want 研究能够输出个人最小可行验证路线, so that 研究结果可以进入原型或实验阶段。
34. As a 使用者, I want 研究结果提出实验变量和验证指标, so that 我可以用自己的数据验证假设。
35. As a 使用者, I want agent 完全只读收件箱, so that 模型不能改变原始口播或提前删除待处理条目。
36. As a 使用者, I want 只有验收通过的 `done` 项才会被删除, so that 失败内容始终可以追回。
37. As a 使用者, I want 收件箱修改、移动、重命名和删除都被检测, so that agent 无法绕过处理端的所有权边界。
38. As a 使用者, I want 白名单外的新文件和修改都使整轮失败, so that 模型不会污染 vault 或工具仓。
39. As a 使用者, I want 错误嵌套的 `生活/.../Yan帳/...` 被拒绝并清理, so that vault 永远只有一个顶级 `Yan帳`。
40. As a 使用者, I want 想法文件直接位于 `Yan帳/想法` 下一层, so that 想法不会按日、按月或按主题目录重新分裂。
41. As a 使用者, I want 研究文件直接位于 `Yan帳/研究` 下一层, so that 研究简报的路径长期稳定。
42. As a 使用者, I want 同名想法和研究任务不会静默覆盖旧文件, so that 历史内容和双链不会指向错误对象。
43. As a 使用者, I want 每条本轮收件项都出现在唯一的回执数组中, so that 编排可以判断本轮是否完整。
44. As a 使用者, I want 回执带有当前轮次标识, so that 旧回执不能冒充新一轮结果。
45. As a 使用者, I want 回执声明的日记、想法和研究文件都必须真实存在, so that 处理环不会删除没有写回结果的 inbox。
46. As a 使用者, I want 一轮只处理配置上限内的条目, so that 连续投递不会一次耗尽时间和模型预算。
47. As a 使用者, I want 超过单轮上限的条目留在收件箱, so that 下一轮可以继续处理。
48. As a 使用者, I want 同时只能有一个处理实例, so that 日记、想法和研究不会被并发双写。
49. As a 使用者, I want 锁占用时看到持有进程和创建时间, so that 我能判断是在等待还是遇到陈旧锁。
50. As a 使用者, I want 处理阶段、研究阶段、队列等待和 agent 耗时都有日志, so that 我能知道五条口播当前位于哪一步。
51. As a 使用者, I want 本地模式不执行任何 Git 操作, so that 联调不会污染工具仓或真实日记仓。
52. As a 使用者, I want 生产模式只对 `VAULT_PATH` 执行 Git 生命周期, so that 工具仓和日记仓职责保持分离。
53. As a 使用者, I want 本地真实 Codex 可以使用本机配置的模型和思考能力, so that 我可以固定 `gpt-5.6-luna` 与 `max` 进行联调。
54. As a 开发者, I want 用临时 vault 和假 agent 验证完整处理循环, so that 测试不依赖真实来源、真实远程 Git 或模型回答。
55. As a 开发者, I want 用假研究来源验证研究简报写回, so that 研究状态、来源和双链具备确定性回归测试。
56. As a 开发者, I want 研究来源检索通过可替换接口注入, so that 外部网络不可用时仍能测试证据验收。
57. As a 开发者, I want 真实 Codex 研究只做人工 smoke test, so that 自动化测试不会依赖模型措辞或外部站点稳定性。
58. As a 开发者, I want 研究阶段和内容整理阶段可以独立失败, so that 研究失败不会回滚已经验收的日记和想法。
59. As a 开发者, I want 失败条目经过阈值后进入隔离区, so that 处理环不会无限重复同一错误。
60. As a 开发者, I want 现有收件 HTTP 契约继续通过回归测试, so that 研究功能不会改变捕捉端投递语义。

## Implementation Decisions

### 领域状态与触发

- `想法`、`待查`、`研究任务`和`研究简报`继续保持四个不同概念。想法回答是否值得离开今天单独回看，待查回答是否存在认知缺口，研究任务回答是否要主动搜集和核验资料，研究简报保存研究输出。
- `needs_research: true` 继续作为候选信号。研究 runner 在内容整理阶段验收完成后自动消费候选，不等待用户再次点击或输入权限。
- 研究任务状态至少包括 `pending`、`running`、`partial`、`blocked` 和 `complete`。`refresh` 作为更新操作记录，不作为完成状态。
- `complete` 只有在研究问题、证据、来源、不同观点、未知点、研究时间、来源双链和写回验收全部完成后才能使用。完成后才将 `needs_research` 设为 `false`。
- `partial` 和 `blocked` 保留 `needs_research: true`，记录缺口和下一步；不得写无来源结论。
- 研究任务可以来自日记或想法。若有独立想法，优先将研究任务关联到该想法；若没有独立想法，则关联到源日记并在控制状态中保留任务记录。

研究任务控制记录使用以下决策性字段，具体存储形式由实现选择：

```text
task_id
source_diary?
source_idea?
question
status: pending | running | partial | blocked | complete
created_at
updated_at
brief?
last_error?
```

### 处理阶段和研究阶段

- 一个处理循环持有同一单实例锁，先完成收件箱内容整理，再对已经验收的研究候选执行研究阶段。
- 内容整理阶段负责日记、想法和研究候选，研究阶段负责研究简报。两个阶段不能同时修改同一个来源笔记。
- 内容整理阶段成功后，即使研究阶段失败，已验收的日记和想法也保留；研究任务状态回到 `partial` 或 `blocked`，等待下一次处理环。
- 研究阶段可以在本轮内容整理之后立即运行，也可以由同一队列的合并唤醒继续运行。两种方式对用户都表现为自动处理，不要求手机端再次操作。
- 处理环扫描收件箱时只读取顶层 Markdown 文件，忽略 `_inbox/_quarantine` 和目录项。

### 研究来源和质量规则

- 研究范围不因地区、语言、来源数量、观点数量或问题领域预先收缩。
- 国外和国际来源是固定优先级，包括国外机构、国际组织、国外论文、国外标准、国外数据、原始项目资料和目标领域内的直接来源。
- 国内官方来源可用于说明本地政策、制度文本、当事方立场和本地事实，但不能独立支撑关键结论；需要标明立场、可能的选择性披露和交叉核验结果。
- 重要结论至少记录原始证据、独立确认情况、适用范围、时间、利益关系和限制。
- 研究必须主动寻找最强反方观点、失败案例、相反数据、方法争议和可能推翻当前结论的证据。
- 搜索摘要、转载、聚合页和无法打开的链接只能作为线索。不能编造 URL、作者、标题、日期、数据或访问结果。
- 发现新增来源不再改变主要结论、证据强度和未知点时可以停止，并记录停止依据。
- 研究结果区分事实、推断、建议和未知点。健康、法律、财务和安全主题必须明确证据边界，不能输出缺乏背景的个体化诊断或确定性指令。

### 研究简报写回

- 研究简报一条研究任务一个文件，直接位于顶层 `Yan帳/研究` 下，禁止嵌套目录、日期目录和日记树下的同名目录。
- 简报至少包含研究问题、结论摘要、证据与事实、多视角和对抗审查、未知点与限制、研究范围与方法、来源和关联笔记。
- 来源记录至少包含标题、作者或机构、发布日期、访问日期、完整 URL 或可核验定位、适用范围和限制。
- 研究简报链回源日记或源想法，源日记或源想法追加时间戳、简短钩子和研究简报 wikilink。
- 研究中产生的独立产品方向、假设、实验问题或后续研究记录在简报的后续想法区域，并带有来源简报链接。未经内容整理阶段确认时，不直接覆盖现有想法正文。
- 同一来源和问题的更新优先更新已有简报并记录变更摘要、旧结论状态和证据差异；新任务才创建新文件。

### Vault 路径约束

- 允许的顶级长期目录只有配置得到的 `IDEAS_DIR` 和 `RESEARCH_DIR`，默认分别为 `Yan帳/想法` 和 `Yan帳/研究`。
- 想法和研究只允许各自目录下一层的 Markdown 文件。
- 日记只允许配置日记树下的 `YYYY/YYYY-MM/YYYY-MM-DD.md`。
- `生活/**/Yan帳/**`、`Yan帳/想法/子目录/**`、`Yan帳/研究/子目录/**` 和按年按月分桶的长期内容全部拒绝。
- 机械验收必须检查新增、修改、删除、移动和重命名后的最终路径。发现嵌套 `Yan帳` 等白名单外变更时，整轮失败，并恢复可恢复的新增或修改文件，不能只恢复 inbox 删除。

### 收件箱所有权和回执

- agent 对 `_inbox` 完全只读，禁止修改正文、frontmatter、attempts、删除、移动和重命名。
- agent 只能在回执中声明 `done`、`failed` 或 `quarantine`。收件箱删除和隔离移动由编排脚本执行。
- 每一轮由编排器生成唯一 `round_id`，在 agent 输入和回执中保持一致。验收必须拒绝缺少或不匹配 `round_id` 的旧回执。
- 回执必须覆盖本轮快照内每一条收件项，且每条只能出现一次。漏报、重复 inbox、重复 idea、快照外 inbox 或旧回执均使整轮失败。
- `done` 必须声明真实存在的日记，声明想法或研究简报时必须声明合法路径且文件存在。
- 验收失败时所有原始 inbox 保留，失败计次按条目递增；达到阈值或明确 quarantine 时才由脚本移动到隔离区。
- 失败轮不应把上一次成功回执当作当前轮结果。处理器必须在日志和 `STATE` 中记录当前轮失败原因。

### 队列、批处理和日志

- 本地 ingest 收到多次投递时使用合并唤醒：一个处理轮运行期间只保留待处理标记，不为每一条投递创建独立的长链队列。
- 处理轮仍由文件锁保证单实例。运行中的轮结束后，若收件箱或研究任务仍有内容，最多自动继续下一轮。
- 单轮内容整理和研究任务数量继续受配置上限控制；研究来源本身不受固定数量上限限制，以证据增量作为停止条件。
- 日志至少记录队列入列、队列合并、等待时长、锁持有者、阶段开始和结束、选中数量、每阶段耗时、agent 启动和退出、回执验收结果、失败原因、剩余条数和研究状态。
- `STATE.md` 让用户打开 vault 即可看到当前阶段、状态、最后错误、剩余 inbox 数量和待研究任务数量。

### 模型和环境配置

- 模型、思考能力、CLI 路径、超时和单轮上限均由运行配置传入，不写死在 skill 内容中。
- 本地 Codex 联调的默认目标为 `gpt-5.6-luna` 与 `max`，runner 需要把它们转换为 Codex CLI 的显式参数。
- 本地 `VAULT_GIT_MODE=local` 时，内容整理和研究写回都只操作临时 vault，不执行任何 Git 命令。
- 生产 `VAULT_GIT_MODE=remote` 时，所有 Git 生命周期仍只针对 `VAULT_PATH`，工具仓只提供程序、skill 和配置模板。
- 凭证不进入口播、研究简报、回执或 Git 历史。研究 runner 不绕过登录、付费墙、robots 或访问控制。

### 迁移和兼容

- 现有顶级 `Yan帳/想法` 和 `Yan帳/研究` 内容保持可读，现有日记链接不应被改写成嵌套路径。
- 处理环启动时可以检测并报告历史嵌套 `Yan帳`，但自动处理轮不得把它当作合法写回目标，也不得静默合并内容。
- 研究相关的旧 `needs_research` 标记迁移为 `pending` 状态时必须保留来源链接和原始正文。
- 现有 ingest HTTP 响应继续使用 `delivered: true` 表示进入收件箱，不增加研究完成字段。

## Testing Decisions

### 好测试的定义

- 以临时 vault 中的文件、路径、回执、状态、队列结果和轮次结果作为外部行为断言。
- 不断言模型具体措辞、prompt 内部顺序或私有函数调用次数。
- 研究来源用可注入的假来源目录或假来源 adapter 固定证据、冲突和反方资料；真实网络和真实 Codex 只做人工 smoke test。
- 每个失败断言应能指出原文保留、路径越权、回执不完整、状态错误、研究证据缺失或队列行为错误。
- 本地测试不能访问真实 Obsidian vault、真实远程 Git、手机或生产来源凭证。

### 主测试 seam

使用一个最高层处理循环 seam：临时 vault、假 agent、假研究 runner、假来源 adapter、可注入锁、时钟和队列调度器。输入是多条 inbox 和研究候选，输出是日记、想法、研究、回执、STATE、剩余 inbox 和轮次结果。

该 seam 必须覆盖：

1. 五条快速投递最终全部被唯一回执交代，内容整理按日记合并，研究候选进入研究阶段。
2. 明确产品想法创建顶级想法文件，并生成顶级研究简报。
3. 纯日常内容只写日记，不创建研究任务。
4. 三大项视频分析案例生成带国外和国际来源、反方观点、未知点和健康边界的研究简报。
5. 研究完成后关闭 `needs_research`，研究失败时保留候选。
6. agent 修改或删除 inbox 时整轮失败并恢复；nested `Yan帳` 变更被拒绝并清理。
7. 旧回执、漏报、重复 inbox、重复 idea、快照外 inbox 和路径越界均不能删原文。
8. 快速连续唤醒被合并，只有一个 agent 轮持有锁，后续条目不因重复队列而无限等待。
9. 空收件箱和空研究队列立即结束，不调用 agent。
10. 本地模式不调用 Git publisher，工具仓没有 vault 正文变更。

### 现有测试 seam 的回归

- 现有收件 HTTP seam 继续覆盖鉴权、空文本、非法 JSON、时间字段、CORS 和本地只写收件箱。
- 现有处理编排 seam 继续覆盖空收件箱、成功删除、缺 diary、未授权删除、失败计次、隔离、单轮上限、白名单和锁。
- 现有回执验收 seam 增加 round id、漏报、重复、嵌套 Yan帳、新增越权文件和 inbox 修改恢复。
- 现有唤醒 seam 增加多条快速投递的合并调度和队列完成后剩余条数。
- 真实 Codex 联调使用人工测试清单验证模型是否遵守 skill、是否处理全部条目和是否写出合理研究简报，不将其作为稳定自动化断言。

## Out of Scope

- 开发实际的撸铁三大项视频分析模型、姿态估计模型、杠铃检测模型或训练数据集。
- 根据个人视频作医学诊断、伤病概率预测或替代专业医疗判断。
- 自研语音识别、捕捉端分类 UI、多用户、OAuth、每设备 token 和即时通知。
- 把研究结果自动变成完整产品代码、训练计划执行器或自动健身教练。
- 爬取需要登录、付费或绕过访问控制的来源。
- 建立长期搜索索引、全文搜索产品或来源推荐产品。
- 修改真实 Obsidian vault、真实远程 Git、VPS、cron、systemd 和生产冲突演习的自动化测试。
- 重新设计捕捉端视觉和重新定义 Yan帳 顶级目录。
- 对历史嵌套目录做无确认的内容合并或自动删除。

## Further Notes

- 本规格对现有 `processor-loop` 规格中真调研属于范围外的决定进行增量替换；收件、日记、想法、锁、隔离和本地生产边界继续继承原规格。
- 顶级 `Yan帳` 是固定领域决策，任何研究、想法和路径验收实现都必须遵守 ADR-0006。
- 研究 skill 定位为研究执行与研究简报写回层。内容整理 skill 负责从口播提炼想法轴和待查轴，处理环负责调度与机械验收。
- 研究简报的准确性、来源质量和反方覆盖需要人工样例迭代；自动化测试负责契约和状态，不能证明模型的知识质量。
- 实现顺序建议为：先修复处理循环的 round id、收件箱只读、越权路径恢复和队列合并，再接研究 runner 和假来源 seam，最后进行真实 Codex 与研究来源 smoke test。
