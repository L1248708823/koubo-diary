# Spec: Yan帳 v1.1 日记整理、想法关联与研究判断

Status: ready-for-agent
Feature slug: `yan-account-v11-content-research`
Sources: `CONTEXT.md`、`docs/ops/post-deployment-handoff-2026-08-04.md`、ADR-0006、ADR-0008 至 ADR-0018、现有处理 skill、现有研究 skill、当前处理编排和测试

## Problem Statement

项目已经上线 v1.1，收件项可以进入日记，符合条件的内容可以生成想法，也可以登记研究任务。上线后的主要问题集中在内容判断和研究方式，现象已经记录在运维交接文档中，但其中的推论没有直接作为产品决策使用。

本 spec 只固定已经讨论确认的产品方向，保留已经完成的收件、锁、回执、路径和写回基础设施。需要解决的重点有以下几项：

1. 日记需要轻度整理，必须保留用户的情绪、语气、犹豫和原本没有解决的问题。
2. 想法不能由 `我想` 等关键词直接触发，需要根据内容是否形成长期可回看的命题判断。
3. 昨天的想法可能在今天继续发展，AI 需要能够关联已有想法和研究，减少重复文件。
4. `待查`、研究任务和研究简报需要连成一条链，不能停在标记阶段。
5. 研究方式需要适应技术问题和其他领域的问题，不能被固定章节、固定搜索次数或固定观点数量限制。
6. Codex 主处理端和独立研究进程必须使用明确的模型和思考程度，不能依赖 CLI 默认值。

## Solution

保留现有处理顺序，并把内容判断写成可执行契约：

`收件项 → 日记轻度整理并写回 → 判断想法和待查 → 关联或创建想法和研究任务 → 启动研究 → 更新研究状态和链接`

日记负责保存当天发生的内容和个人声音，想法负责保存脱离当天仍值得回看的用户命题，研究任务负责回答确实需要外部资料或核验的问题，研究简报负责保存研究过程、证据、分析和建议。每一层都有自己的职责，研究结果不会自动改写成用户已经确认的想法。

AI 可以读取顶层 `Yan帳/想法` 和 `Yan帳/研究` 的直接子 Markdown 文件，用于判断后续内容是否延续已有内容。它仍然不能扫描整个 vault，也不能读取与当前处理无关的目录。

研究提示词采用问题驱动的方式。固定保留用户明确要求的反模式和事实边界，其他内容交给模型根据问题选择合适的回答角色、研究方法和表达结构。

## User Stories

1. 作为使用者，我希望每条验收成功的收件项都进入对应日期的日记，这样时间线不会断裂。
2. 作为使用者，我希望日记只做错别字、标点、断句和排版等轻度整理，这样原本的说话方式不会被改成 AI 文风。
3. 作为使用者，我希望日记保留情绪、语气、犹豫、强调、未决问题和现场语境，这样回看时仍然能理解当时的状态。
4. 作为使用者，我希望收件项验收完成后仍按原流程清理，不额外保存原文，这样 vault 不会出现重复的原始记录。
5. 作为使用者，我希望同一天的多条收件项写入同一篇日记，并按 `captured_at` 排序，这样 Obsidian 中的时间线稳定可读。
6. 作为使用者，我希望只有明确形成长期命题的内容才进入想法库，这样短期情绪和当天流水不会堆积在那里。
7. 作为使用者，我希望 `我想`、`我发现` 等句式只作为判断线索，不能直接决定分类，这样 AI 不会根据关键词误建想法。
8. 作为使用者，我希望一条收件项中的多个独立想法可以分别保存，前提是拆开后每条仍然能独立理解，这样不同命题不会被混在一个文件里。
9. 作为使用者，我希望判断不清楚时不自动合并到已有想法，这样历史内容不会被模型猜错后覆盖。
10. 作为使用者，我希望昨天的想法在今天继续发展时更新原想法并关联新的日记，这样一个长期命题不会产生大量重复文件。
11. 作为使用者，我希望想法文件名使用捕捉日期，这样在 Obsidian 中按文件名排序时能看出它最早出现的时间。
12. 作为使用者，我希望想法保留来源日记链接和完整捕捉时间，这样长期内容仍然可以回到当时的上下文。
13. 作为使用者，我希望存在具体问题且确实需要资料、核验或比较时自动登记研究任务，这样研究可以接在内容处理后继续进行。
14. 作为使用者，我希望已有知识和推理足够回答时不强行创建研究任务，这样普通的思考不会被变成无意义的调研。
15. 作为使用者，我希望研究任务可以同时关联想法和源日记，也可以只关联源日记，这样事实问题不需要先伪装成想法。
16. 作为使用者，我希望同一个问题出现新资料时更新原研究任务和研究简报，问题发生变化时创建新的任务并互相链接，这样研究历史不会混在一起。
17. 作为使用者，我希望日记写回后研究阶段能够自动接着运行，不需要我再发送一条日记才能触发研究。
18. 作为使用者，我希望研究方式能适应产品、技术、生活和其他领域的问题，这样不同问题可以使用真正合适的分析方式。
19. 作为使用者，我希望在确实需要比较方案时看到多种真实可行的方案、详细优缺点和明确推荐理由，这样我能据此做决定。
20. 作为使用者，我希望没有三种真实方案时直接说明原因，不要为了满足数量编造方案。
21. 作为使用者，我希望有争议、比较或较高风险时才看到反方观点，这样反方审查有实际作用，不会变成固定段落。
22. 作为使用者，我希望研究中的事实、推断、建议和未知点能够区分，并且外部事实有可核验来源，这样我能知道结论的依据。
23. 作为使用者，我希望搜索时不使用中文网站作为信源，也不编造来源、链接、作者、日期、数据或搜索结果。
24. 作为使用者，我希望研究完成后只更新研究状态、待查状态和链接，不自动把想法标成已验证或已实现。
25. 作为开发者，我希望内容整理和研究阶段读取范围明确，这样允许关联已有内容时仍不会泄露整个 vault。
26. 作为开发者，我希望主处理端和独立研究进程都显式使用 `gpt-5.6-luna` 与 `max`，这样本地和生产行为不会受 CLI 默认值影响。
27. 作为开发者，我希望用最高层处理轮测试日记、想法、研究、回执、STATE 和剩余收件项，这样测试覆盖真实产品链路。

## Implementation Decisions

### 处理顺序与触发时机

- 内容处理阶段先读取本轮 `pendingInbox`，完成日记写回，再判断想法轴和待查轴。
- 想法轴和待查轴可以同时成立。四种结果分别是只写日记、日记加想法、日记加研究任务、日记加想法加研究任务。
- `待查` 只表示存在具体的认知缺口。它可以出现在日记或想法上，不能只因为语气中出现疑问词就创建研究任务。
- 研究任务在内容处理写回并通过验收后进入现有研究流程。用户不需要再次发送日记，也不需要输入第二个触发词。
- 昨天的想法是否在今天继续发展，在处理今天的新收件项时判断。判断依据是新内容与已有想法的主题、命题和发展关系，不依据日期或关键词。
- 研究 runner 仍沿用现有的任务消费和状态更新流程。本 spec 调整任务判断、关联、研究提示词和写回边界，不重新设计整个调度系统。

### 日记轻度整理

- 每条收件项都必须写入对应 `captured_at` 日期的日记。多条收件项写入同一天时使用同一文件，每条单独成段，按 `captured_at` 升序排列。
- 整理范围限于错别字、标点、断句、段落和明显影响阅读的排版问题。
- 允许删除完全没有语义作用的卡顿残片，或同一个词连续重复后立即改口、纠正形成的机械重复。删除后不能改变原本的意思、情绪、犹豫、强调和语气。
- 不建立固定的删词清单。`就是`、`然后`、`那个` 等词不能因为出现就自动删除；如果它表达了语气、停顿、犹豫、转折或现场感，就必须保留。
- 为了强调情绪而重复的词句必须保留。用户没有说清楚的部分、未决问题和自我怀疑不能被 AI 补成结论。
- 整理只在单条收件项内部进行，不跨收件项合并句子，不替用户补充背景，不提高文风，不改写成总结。
- 日记可以保留想法的短钩子和 wikilink，但不复制想法全文。想法文件中保存用户明确表达的内容。
- 收件项验收通过后按原有流程清理。v1.1 不新增原文归档、原文副本或隐藏备份。

### 想法判定与写回

只有在以下条件同时满足时，才把内容作为想法处理：

1. 用户明确表达了观点、假设、创意、产品方向、生活命题或可复用方法。
2. 去掉日期、地点、当时的具体场景和短期情绪后，内容仍然能够单独理解。
3. 未来回看时仍有价值，值得作为一个长期命题保留。

`我想`、`我发现`、`我觉得`、反问句和类似表达只提供线索，不能单独触发想法。AI 不得根据关键词推断用户没有说出的观点。模糊念头只留在日记中。

一条收件项包含多个内容时，只有在每个内容单独拿出来仍能理解、且不需要 AI 添加上下文时才拆成多个想法。拆开会改变意思或必须补充背景时，保留为一个想法或只写日记，具体取决于内容是否达到想法判定条件。

想法文件直接位于配置的 `IDEAS_DIR` 下一层，文件名使用 `YYYY-MM-DD-短标题.md`，日期取收件项的捕捉日期，后续修改不改变日期。文件冲突时不能覆盖旧文件，应使用可追踪的后缀或新标题。

想法文件至少保留：

- 用户的轻度整理正文。
- 完整捕捉时间。
- 来源日记 wikilink。
- 与研究任务有关时的研究状态或研究链接。

当新内容明确延续已有想法时：

- 读取并更新已有想法文件，保留旧正文和旧来源。
- 追加本次新增内容、捕捉时间和新的日记链接，不能用新内容覆盖历史判断。
- 日记关联到这个已有想法，回执使用已有想法路径。

当新内容本身符合想法条件，但与已有想法的关系不确定时，创建新的日期想法，不能自动合并。两个已经存在的旧想法之间也不自动合并。

研究结果、研究建议和 AI 推断不自动写成用户的想法。它们需要留在研究简报或研究任务的后续区域，除非用户以后明确表达并再次经过想法判断。

### 研究任务判定与关联

研究任务只在问题确实需要外部资料、事实核验、当前信息、方案比较、可行性判断或其他证据支持时创建。用户明确要求调研、来源或核验时，按用户要求进入研究任务。

这是一组帮助模型判断搜索需要的方向。模型先判断已有知识和推理是否足够解决问题；足够时直接处理，不为了满足规则而搜索。涉及会随时间变化的事实、用户明确要求来源、需要核验的具体说法时，通常需要外部核验。健康、法律、财务和安全问题只有在确实影响实际判断时才需要特别说明证据边界，不因为领域名称单独触发一套固定流程。

研究任务可以来自一个想法、一个日记问题，或两者同时存在。没有独立想法的事实问题直接关联源日记，不强行创建想法。

AI 可以读取 `RESEARCH_DIR` 的顶层研究简报和当前任务记录，用于判断后续内容是否延续已有研究：

- 同一个问题出现新资料、新证据或新的验证阶段时，更新原任务和原研究简报。
- 问题的目标、范围或核心假设发生变化时，创建新的研究任务和研究简报，并链接旧任务或旧简报。
- 判断是否为同一研究不清楚时，不自动合并，保留独立任务并记录来源关系。
- 研究完成后更新任务状态、待查状态和链接，不自动更新想法的确认状态，不自动标记已验证或已实现。

### 研究方式与输出

- 研究可以服务于技术问题、产品方向、工作方式、生活决策和其他领域的问题。模型根据问题选择合适的分析角色和方法。
- 不固定研究章节、来源数量、来源类型、搜索轮数或每个问题必须回答的栏目。研究简报仍然必须让读者看得出问题、范围、证据、分析、建议、未知点和来源之间的关系。
- 事实、推断、建议和未知点分开表达。外部事实、数据、论文或原始资料支撑的结论需要提供可核验来源；无法核验时明确写成未知，不补写来源信息。
- 需要比较方案或用户正在做选择时，默认提供至少三种真实可行的方案。每种方案都要说明适用条件、主要优点、主要缺点、实施代价和风险，并明确说明我为什么推荐其中一种。确实不足三种时说明原因，不编造方案凑数量。
- 反方观点只在存在争议、需要比较、风险较高、结论可能影响较大或用户明确要求时主动寻找。反方需要说明它会改变结论的哪一部分；没有可靠反方资料时，写成待验证的反向假设。
- 搜索时不使用中文网站作为信源。搜索摘要、转载、聚合页和无法打开的链接只能作为线索，不能伪装成已经核验的证据。
- 能用已有知识和清晰推理解决的问题，不强行搜索。确实需要外部资料时，根据证据增量、时间、调用和网络限制决定何时停止，并在简报中说明停止原因。
- 研究提示词不能为了形式强迫模型套用总分总、固定分点或固定结论。简单问题直接回答，复杂问题按实际依赖关系展开。

### AI 表达和反模式

以下内容属于固定反模式，研究问题的具体领域和方法不受下面规则之外的额外硬编码限制：

- 永远不要使用用户禁止的转折句式。
- 不出现破折号。
- 不使用无关的比喻、空洞的排比和没有信息量的抽象形容词。
- 表达观点时使用“我”，例如“我认为”“我觉得”“我猜”。研究简报中的专业事实、引用和机器字段按其自身格式表达。
- 用自然、直接、容易读懂的中文回答。简单问题直接回答，复杂问题再展开。
- 不省略会影响理解的主语、条件、因果关系和结论。用户读不明白时，换成更直白的说法。
- 任务目标是解决问题，同时检查用户前提是否成立，必要时提出建设性的怀疑和替代方案。
- 不编造来源、链接、作者、日期、数据、工具结果和已经完成的动作。
- 不因为提示词里出现“推荐三种”“反方”“搜索”等词就机械执行；是否需要这些内容由问题决定，方案比较和高风险判断除外。
- 日记和想法保留用户的表达方式，不加入 AI 的语气、结论和评价。

研究简报可以使用对应领域的正常表达方式。回执、`STATE.md` 和 frontmatter 的机器字段继续使用严格格式，不能为了口语化破坏解析契约。

### AI 可读范围与写入边界

内容整理 agent 的可读范围调整为：

- 本轮快照中的 `pendingInbox` 文件。
- 本轮收件项对应的目标日记。
- `PROCESSOR_DIR/research-tasks.json` 和必要的上一轮回执。
- 配置的 `IDEAS_DIR` 顶层直接子 Markdown，用于判断想法延续关系。
- 配置的 `RESEARCH_DIR` 顶层直接子 Markdown，用于判断研究延续关系。

允许读取想法和研究目录不等于允许扫描整个 vault。禁止读取或枚举父目录、日记树中无关日期、工具仓、`.git`、`.env`、密钥、临时目录和嵌套的长期内容目录。`IDEAS_DIR` 和 `RESEARCH_DIR` 仍然只接受顶层 Markdown 文件，不能通过子目录规避边界。

内容整理 agent 只能写入本轮目标日记、想法、研究任务记录、暂存目录和回执路径。收件箱正文、frontmatter、删除、移动和隔离仍由编排器管理。研究 agent 只能写当前任务指定的研究简报、来源笔记和任务状态。

### Codex 运行参数

所有 `codex exec` 调用和独立 research 进程都必须显式传入：

```text
model: gpt-5.6-luna
model_reasoning_effort: max
```

配置不能依赖 CLI 默认模型或默认思考程度。主处理端、研究 runner、测试用假 runner 和本地 smoke test 都要能观察到这两个参数，测试不依赖模型具体措辞。

### 提示词维护

- 领域和内容判断规则维护在处理 skill，研究方法和研究写回规则维护在 research skill。
- 运行时 prompt 负责注入本轮上下文、路径、可读范围、可写范围、回执要求和模型参数，不复制一份容易过期的完整规则。
- skill、运行时 prompt、回执验收和代码实现出现冲突时，先统一契约，再修改实现。机械验收负责决定文件和状态是否接受，模型文字不能替代验收。
- 产品规则尽量使用判断原则和例外边界，不建立无必要的关键词黑名单、固定分类清单和强制章节清单。

## Testing Decisions

### 主要测试 seam

使用现有最高层处理轮作为主 seam，注入临时 vault、多个收件项、已有想法、已有研究简报、假内容整理 agent、假 research runner、时钟、锁和工作区。验证实际输出：日记、想法、研究任务、研究简报、回执、`STATE.md`、剩余收件项和模型参数。

现有 prompt 构建、Codex runner、回执验收、研究写回和路径验收测试继续作为辅助 seam。自动化测试不锁定模型的具体句子、段落顺序或偶然的标题措辞。

### 必须覆盖的内容样例

1. 纯日常经历只写日记，情绪和语气保留。
2. 含有错别字、标点问题和断句问题的日记只做轻度整理。
3. 连续重复后立即改口的机械重复可以删除，为了强调情绪的重复必须保留。
4. `我想` 出现但没有形成长期命题时不创建想法。
5. 没有关键词但明确提出产品方向、假设或方法时创建想法。
6. 同一天多条收件项写入同一日记，顺序按 `captured_at`，内容不跨项合并。
7. 一条收件项包含两个互不相关且都能独立理解的想法时创建两个想法。
8. 一条收件项拆开后必须补上下文时不拆。
9. 新内容明确延续已有想法时更新原想法并新增日记链接，旧正文不丢失。
10. 新内容与已有想法关系不清时不自动合并；如果新内容符合想法条件，创建新的日期想法。
11. 新内容明确延续已有研究时更新原任务和简报，问题变化时创建新任务并互链。
12. 有具体外部问题但没有独立想法时创建研究任务并关联源日记。
13. 个人偏好或已有知识足够回答的问题不创建研究任务。
14. 研究在日记写回并验收后继续运行，不等待用户再次发送日记。
15. 需要方案比较时给出至少三种真实方案并详细比较；真实可行方案不足三种时说明原因。
16. 简单问题不强行搜索、不强行反方、不强行分点；争议或高风险问题进行有针对性的反方审查。
17. 搜索结果不包含中文网站信源，无法核验的资料不写成确定事实。
18. 研究结果不会自动把想法标成已验证或已实现。
19. 内容整理 agent 可以读取顶层想法和研究文件，但不能读取整个 vault 或无关目录。
20. 主处理端和独立 research runner 的实际调用参数均为 `gpt-5.6-luna` 与 `max`。
21. 收件项验收完成后按原流程清理，vault 中没有额外原文副本。

### 验收标准

- 每条 `done` 收件项都有且只有一处对应的日记写回，日记路径和回执符合现有契约。
- 日记轻度整理不会删掉用户的情绪、犹豫、强调和未决内容，也不会跨收件项合并。
- 想法判定不依赖关键词，想法文件名包含捕捉日期，延续关系明确时保留原文件并追加关联内容。
- 研究任务只在存在具体问题和实际证据需求时登记，研究状态可以从 pending 进入后续状态，链路不会停在待查标记。
- 同一研究问题得到更新，变化后的问题获得独立任务，研究结果不会擅自改变用户观点状态。
- 研究输出对技术和非技术问题都可用，比较方案时有真实依据和推荐理由，研究结构随问题调整。
- 读取范围允许顶层想法和研究关联判断，同时拒绝整个 vault 扫描和越权写入。
- 模型参数显式传入，现有全量测试、类型检查和相关人工 smoke test 通过。

## Out of Scope

- 重写已经上线的收件投递、锁、回执、隔离、路径和 Git 生命周期基础设施。
- 给用户增加分类按钮、研究开关、关键词配置、全文搜索或多用户权限。
- 为想法保留额外的原文归档、副本或隐藏历史文件。
- 自动合并两个已有的旧想法，或无确认迁移历史目录中的内容。
- 把研究结论自动写成用户想法、已验证结论、已实现功能或产品代码。
- 建立固定的研究章节、固定来源数量、固定搜索轮数和固定反方数量。
- 为所有问题强制搜索，或为所有健康、法律、财务和安全相关词语自动启动同一研究流程。
- 使用中文网站作为研究信源，或绕过登录、付费墙、robots 和其他访问控制。
- 证明模型对所有内容的判断绝对正确。内容质量仍需通过样例审查和后续使用反馈迭代。

## Further Notes

这份 spec 以已确认的产品方向为准。交接文档中的现象和推论需要分别对待，不能把推论直接当作已经决定的规则。

旧的 `.scratch/yan-account-domain-contract/spec.md` 中关于额外保存原文、关键词式分类、自动合并限制和固定研究结构的部分已经过时，实施时以本 spec 和对应 ADR 为准。

实现建议按以下顺序拆票：先同步处理 skill、运行时 prompt 和可读范围，再实现想法与研究的关联写回，然后补齐研究 runner 的显式模型参数，最后补充最高层处理轮测试和人工 smoke test。实现阶段保持现有用户数据和未提交改动，不做无关重构。
