# Spec: Yan帳 领域与内容整理契约

Status: ready-for-agent
Feature slug: `yan-account-domain-contract`
Sources: `CONTEXT.md`、ADR-0005、ADR-0006、ADR-0007、现有处理 skill、研究 skill、当前项目审查结论

## Problem Statement

项目的处理链路已经可以把收件项写入日记、抽取想法并登记研究任务，但产品主题、用户文案和领域词仍混用旧的「口播」称呼。现有 glossary 将 Yan帳 定义为长期内容空间，用户则已经确认 Yan帳 是产品主题和用户可见总称。

内容整理规则也分散在 glossary、处理 skill、运行时 prompt 和机械验收中。运行时 prompt 声称包含完整规则，却只提供了部分摘要，同时禁止 agent 读取 skill。这样会让日记语气、想法判定、待查标记和研究任务登记依赖模型当时是否记得隐含规则。

现有规则对日记、想法、待查和研究任务已有基础区分，但对长期目标、当天计划、相似想法、混合内容、研究结果产生的新想法以及研究权限的边界仍不够明确。测试可以锁住路径和状态契约，无法单独决定这些业务语义。

## Solution

建立 Yan帳 的统一领域语言和内容整理契约：Yan帳 负责产品主题与用户体验，收件项负责表示一条待处理的原始记录，日记负责时间线，想法负责脱离当天仍可回看的长期命题，待查负责标记认知缺口，研究任务负责执行一次资料核验，研究简报负责保存带证据的研究输出。

处理 agent 使用一份可追溯的语义规则来源。运行时只注入本轮上下文、路径和硬性操作限制，不能声称已经提供完整规则却实际遗漏内容。机械验收继续作为最终边界，模型输出不能替代文件、路径、回执和状态检查。

本规格保持现有处理主链路和 vault 目录结构，只收紧领域命名、内容判断和提示词维护方式。

## User Stories

1. As a 使用者, I want 页面和产品说明统一使用 Yan帳, so that 产品主题与实际体验一致。
2. As a 使用者, I want 原始记录、日记、想法和研究内容保持清晰区分, so that 我能知道每类内容承担什么作用。
3. As a 使用者, I want 收件项保留原始文本和捕捉时间, so that 整理失败时仍能追回原始内容。
4. As a 使用者, I want 每条已处理收件项进入对应日期的日记, so that 时间线不会断裂。
5. As a 使用者, I want 日记保留个人声音、过程、情绪和现场语境, so that AI 不代替我重写经历。
6. As a 使用者, I want 同一天的多条记录合并进同一篇日记, so that 回顾入口保持稳定。
7. As a 使用者, I want 日记不重复粘贴完整想法正文, so that 时间线和长期内容各自保持清晰。
8. As a 使用者, I want 稳定的原则、假设、产品方向或可复用方法生成独立想法, so that 长期内容可以脱离日期检索。
9. As a 使用者, I want 想法允许保留第一人称, so that 内容仍然属于我的判断和表达。
10. As a 使用者, I want 想法去掉今天、刚才和会议现场等背景后仍可理解, so that 想法具备长期回看价值。
11. As a 使用者, I want 当天计划、临时情绪和单纯事实默认只进入日记, so that Yan帳 不会堆积短期噪音。
12. As a 使用者, I want 一条记录包含多个语义单元时分别判断, so that事实、感受、想法和待查问题不会被混成一个结论。
13. As a 使用者, I want 待查只表示存在认知缺口, so that 标记待查不会立即制造一篇研究简报。
14. As a 使用者, I want 没有长期命题的研究问题仍可关联源日记, so that 研究不强迫先创建想法。
15. As a 使用者, I want 长期想法和认知缺口可以同时成立, so that一个产品方向既能长期保存，也能进入研究。
16. As a 使用者, I want 研究任务保留原始问题, so that研究范围不会被模型替换成另一个问题。
17. As a 使用者, I want 研究结果中的新方向先留在简报中, so that未经确认的推断不会直接变成正式想法。
18. As a 使用者, I want 相似想法不会被静默覆盖或合并, so that历史判断仍然可追溯。
19. As a 使用者, I want 无法确定是否应抽取想法时保留日记, so that内容不会因分类不确定而丢失。
20. As a 使用者, I want 研究失败时保留原始记录、日记和想法, so that外部来源问题不会造成内容丢失。
21. As a 使用者, I want 用户可见文案使用 Yan帳，技术实现仍可使用准确的内部名称, so that品牌和代码边界都清楚。
22. As a 开发者, I want 处理 skill 的语义规则有唯一维护来源, so that模型行为不会因 prompt 摘要漂移。
23. As a 开发者, I want 运行时 prompt 只负责注入本轮上下文和操作限制, so that它不会复制一套容易过期的领域规则。
24. As a 开发者, I want 机械验收继续检查路径、回执和状态, so that模型不能通过自然语言绕过写回契约。
25. As a 开发者, I want 用混合内容和负面样例进行人工审查, so that内容质量不被少量自动化测试替代。

## Implementation Decisions

### 领域语言

- `Yan帳` 是产品主题和用户可见总称，代表记录、整理和长期回看的个人系统。
- `收件项` 是一条已经投递、等待处理的原始记录；它可以来自语音输入法，也可以来自其他捕捉方式。
- `收件箱` 是收件项的投递区。收件项正文和 frontmatter 由脚本管理，agent 不修改或删除。
- `日记` 是按日期组织的回顾正文，承担时间线和个人现场语境。
- `想法` 是可以脱离当天单独理解的原则、假设、产品方向、生活命题或可复用方法。
- `待查` 是日记或想法上的认知缺口标记，不等同于研究任务。
- `研究任务` 是一次主动搜集、核验和整理资料的工作，必须保留来源和原始问题。
- `研究简报` 是研究任务的证据型输出，不承担正式想法的分类职责。
- `回执` 和 `STATE` 是处理环的机器状态，不属于 Yan帳 的个人内容。

### 内容分类

每条收件项独立判断想法轴和待查轴，两条轴可以组合：

- 两轴都否：只写日记。
- 只有想法轴：写日记并创建想法。
- 只有待查轴：写日记并登记研究任务，研究任务关联源日记。
- 两轴都为是：写日记、创建想法并登记研究任务。

分类不确定时，保留原始内容和日记，避免凭猜测创建长期内容。研究任务只在问题具有外部事实、可行性、比较或证据缺口时登记，个人偏好和情绪确认不自动变成研究任务。

### 日记写回

- 每条成功处理的收件项至少更新对应日期的日记。
- 日记保留日期、过程、事实、情绪、现场语境、个人判断和未决问题。
- 整理只删除口头重复、赘词和明显断句问题，不升格文风、不扩写观点、不代作者下结论。
- 日记侧只保留想法的时间钩子和 wikilink，不复制完整想法正文。
- 同一收件项重试时必须保持幂等，不重复追加。

### 想法写回

- 一条想法一个文件，位于 `Yan帳/想法` 的下一层。
- 想法可以使用第一人称，但去掉当天背景后仍需能说明命题、判断、假设或方法。
- 当天计划、短期目标、情绪宣泄和无稳定命题的事实默认不创建想法。
- 标题相似不代表语义相同，v1 不做静默语义合并；无法确认时保留独立文件，交给人工复查。
- 想法必须与源日记互链；研究结果产生的新想法先留在研究简报的后续区域。

### 研究边界

- 待查与研究任务分离。v1 继续沿用现有研究阶段的自动消费策略，不新增 `off`、`ask` 或多级权限模式。
- 研究 skill 负责证据、反方、未知点、来源和写回状态；内容整理 skill 只负责登记研究任务。
- 健康、法律、财务和安全主题必须标明证据边界，不能输出个体化诊断或确定性指令。
- 研究失败或证据不足时保留 `needs_research: true`，不把中间内容标记为完成。

### 提示词维护

- 领域词维护在 glossary，内容判断维护在处理 skill，研究流程维护在 research skill。
- 运行时 prompt 注入当前 round、收件项清单、配置路径、读写限制和回执要求。
- 运行时 prompt 不得声称包含完整规则却只提供摘要。要么注入指定 skill 的完整内容，要么允许 agent 读取被明确指定的 skill。
- 机械验收代码继续负责路径、回执、文件存在性、收件箱所有权和研究状态；提示词不能替代机械验收。
- 用户可见的「口播」统一改为 Yan帳 或具体的「记录」文案；技术包名、环境变量和历史路径不在本规格中强制重命名。

## Testing Decisions

### 好测试的定义

测试只断言对外行为和稳定契约，不把现有测试样例当成完整业务模型。内容边界还需要人工样例审查，重点观察作者语气、时间依赖、长期可回看性和事实与推断的分离。

### 主要验证 seam

- 以最高层处理轮作为主 seam，注入临时 vault、假 agent、假研究 runner、时钟和锁，验证四种分类组合以及失败保留行为。
- 以处理 agent prompt 构建 seam 验证运行时上下文、路径限制和 skill 内容来源一致。
- 以捕捉端构建和页面检查验证用户可见文案使用 Yan帳，投递语义仍然只表示进入收件箱。
- 以人工内容审查清单验证混合内容、长期目标、重复想法、第一人称、纯情绪和研究后续想法。

### 必须覆盖的语义样例

- 纯当天经历，只写日记。
- 当天经历中包含稳定产品方向，日记加想法。
- 只有一个事实核验问题，没有长期命题，日记加研究任务。
- 长期产品方向同时有可行性问题，日记、想法和研究任务并存。
- 一条收件项同时包含事实、情绪、判断和后续问题，各部分不混成单一结论。
- 研究简报失败、部分完成、产生新想法和已有相似想法。

## Out of Scope

- 重写处理编排器或改变 vault 的主路径。
- 自动合并历史想法、迁移历史嵌套目录或删除真实 vault 文件。
- 新增用户分类界面、标签系统、全文搜索或多用户权限。
- 重新设计捕捉端视觉，仅统一用户可见命名和必要文案。
- 证明模型内容分类质量已经达到绝对正确。
- 重新设计研究权限模式。

## Further Notes

当前历史规格和部分运维文档仍使用旧产品称呼。它们应在实现 ticket 中分批同步，技术包名和环境变量可以保留，避免一次性重命名扩大变更范围。
